## 1. 工作方法与工具链

### 1.1 AI 辅助开发的方法论

本项目（尤其本会话）遵循一套可复用的工程纪律，而非"想到哪改到哪"：

- **根因优先（systematic-debugging）**：任何 bug 先做根因调查再动手。四阶段——根因调查→模式分析→单一假设最小验证→实现修复。铁律："没有根因调查就不修复"。本会话每个问题都先复现、定位到具体代码行，再改。
- **需求对齐（brainstorming）**：新功能先分类（spike/bounded/architectural），bounded 任务在聊天里给短设计、拿到确认才实现。云端向量化功能即先澄清"DeepSeek 无 embeddings 接口"这一约束，用户选定"只用本地"后才动手。
- **测试驱动（TDD）**：先写失败测试（红）→实现（绿）→重构。本会话新增 `visionRouting.spec.ts`、`freeAnswerStyle.spec.ts`、`autoKb.spec.ts`；对**有意变更**的旧契约（风格指令行、稳定前缀字节）同步更新测试锚点，而非删测试绕过。
- **完成前验证（verification-before-completion）**：声称"修好了/达标了"之前必须跑命令拿到证据。延迟、召回率、关键词覆盖都用实测数字说话，不凭感觉。
- **记忆持久化**：跨会话的关键事实（知识库结构、修复根因、工具用法、provider 约束）写入项目记忆，避免重复踩坑。

### 1.3 测量台自身的陷阱（会静默产出假数据）

这是本项目最值得记住的经验之一——**测量工具本身会骗人**：

- 遗留 sidecar 占着 `:10097`，导致连续两轮测的是旧代码（修：开跑前检查端口、结束回收子进程）。
- Python 进度条把日志写成二进制，使 `grep` 失配，看似"没输出"。
- 本会话：把 Electron GUI 进程输出 pipe 给 `head`，head 提前退出 → `console.log` EPIPE → 主进程未捕获异常弹无法关闭的错误框（修：重定向到文件再 tail）。
- 共享 capture clock 让已关闭会话的尾句查到新会话锚点，返回未来 ~10s 的时间戳（表现为 e2e 负值）。

教训：测出"好得反常"或"坏得反常"的数字时，先怀疑测量台，再怀疑被测对象。

### 1.4 授权与协作边界

- 凭据只经使用者本人的 shell，AI 执行策略禁止在命令里使用 Key（真实 provider TTFT 因此标为"未测"，不假装测过）。
- 重启用户 live 实例、提交代码等动作先确认或获明确授权；本会话提交由用户明确要求后执行。
- 需要产品决策的变更（如投机作答的重复计费）不单方面落地。

## 2. 主线一：语音解码延迟（ASR）

### 2.1 问题

本地 ASR 打通后，语音结束→出字（e2e）约 **1.85s**，是用户最先感受到的等待。初始猜想是 `speechEndTs = epoch + endMs` 的重建偏置。

### 2.2 拆解（推翻猜想）

`tools/latency-asr-local.sh` 用已知录音驱动真实链路（PipeWire 监听→VAD→sidecar→出字），打印 sidecar 侧端点化等待与解码耗时：

| 组成 | 修复前 | 说明 |
|---|---|---|
| sidecar 端点化等待 | 1200–1800ms | 静默按整块 600ms 累加，700ms 阈值永远要等第二块（固定 1200ms 下限） |
| 整句 CPU 解码 | 600–1900ms | 与输入长度正相关，机器负载敏感 |
| 应用自身 | ≈ 0 | 时钟对齐后确认 |

**猜想错了**：重建偏差实测只有 3–65ms，不是 1.5s。真正的成本是端点化等待 + CPU 解码，与模型无关（nano 与 paraformer 两个引擎差异在噪声范围内）。

### 2.3 修复（每步带实测）

1. **端点化粒度**（`2a469ea`）：块内改按 100ms 回溯扫描静默。`silenceAtTrigger` 达到 700ms，最好一枪 e2e **1791→1299ms**；句子切分也修好（原先两次播放被并成一句 11.4s 的"测试测试"）。
2. **让本地 VAD 来 finalize**（`e83c25a`）：VAD 挂起只有 300ms，早已判定"说完了"，原先只发 status。改成 VAD 关闭时结束会话、下一句用 300ms 前滚缓冲重开。**5 连播 e2e 872–882ms（原 ~1850ms），5/5 转写正确**。代价：句中停顿超 300ms 会切成两段（与 1100ms 答题防抖已有假设一致）。
3. **时钟每会话一份**：按通道共享会导致 e2e 负值（见 §1.3）。

环回接线侧（`L2/L3`）：`pw-link` 并发 + 校验改轮询 + 去固定 150ms 等待 + 起始脏帧按值过滤，**▶→首帧 575→211ms**。

### 2.4 试过并回退的

把整句缓冲裁到语音区间以缩短解码——解码确实随输入长度缩放，但 `sent_buf` 开头多带一个 600ms 前滚块、`sent_begin_ms` 记在另一时间轴，朴素切片会切进词里（"测试"→"嗯，那咋？"）。注释留在代码里，重做需先算对前滚偏移。

### 2.5 依赖可用性缺口

`requirements-funasr.txt` 在干净 Linux 上装不起来（`47fccea` 修文档给可复现配方）：`transformers` 被解析到 4.12.2 → `tokenizers==0.10.3` 需 Rust 源码构建；torch/torchaudio 默认拿 CUDA 变体，无 NVIDIA 机器 `import torchaudio` 报缺 `libcudart.so.13`。

**结果**：ASR 固定开销压到 ~0.9s，剩下主要是 CPU 解码。再往下是 provider TTFT（需用户给 key）与投机作答命中率。

## 3. 主线二：知识库建立

### 3.1 导入管线（v1.0.1 历史工作）

把"导入资料"做成可靠、可见、可增量：

- 逐文件进度上报 + 失败原因写明（格式不支持/扫描版抽不出文字/解析失败/索引未就绪/超 50MB 不读）（`f3612c2`）。
- 内容哈希跳过未变化文件，不重复解析/嵌入（`9d6ed54`）。
- 本地节摘要（PPTX 按幻灯片、带标题按层级），回答跨节文档级问题；每篇 ≤40 节、单次检索 ≤2 条摘要（`72b13ca`、`4adb6ea`）。
- 索引持久化防抖（`3587da4`）、原子写防丢索引（`18104cc`）、嵌入先于清除旧块（`4cb25c8`、`a7ee843`）。
- 导入逻辑抽成可测模块（`6578d2f`）。

### 3.2 预切分词法知识库（本会话）

普通导入用 300 字滑窗，会切断问答表格与公式。对已按小节/题号切好的资料，建一条更准的通道：

- `tools/build-interview-kb.py`：`pdftotext` 提取面经 PDF，按编号知识点/题号切块（**保留作者边界**），清原书水印，附 33→40 组术语别名 + 黄金题集。产出 `991_index.jsonl`（663 块/17 篇：面经整理 266 + 原书 261 + ROS 笔记 124 + 示例代码 12）。
- 切分规则的坑：正文编号列表（"1. 递归要有基准条件…"）会被误判为题号。用三重判定修正——问号结尾 / 结构标记（核心答案/★重点）/ 章内题号顺序递增，且排除句号结尾的陈述句。
- 词法检索（`kbRetrieval.ts`）：BM25 + 别名扩展 + 意图加权（问原理优先通用基础层、问项目优先个人资产层），**零模型、~0.3ms/查询**。

### 3.3 一键自动构建（本会话）

`electron/rag/autoKb.ts` + 设置页"批量构建知识库"按钮：批量选文件/夹 → `extractDocText` 提取 → 结构化切分（md `##`/题号/段落兜底）→ **用已配置的对话 Key** 调 LLM 生成关键词与别名（每篇一次、≤30 篇、失败降级）→ 写索引并自动绑定。无需嵌入模型、无需额外 Key。

### 3.4 稠密向量灌库（本会话，最硬的骨头）

为启用语义融合，需把 KB 逐块向量化进稠密库。遇到本地 ONNX 运行时崩溃：

- **现象**：embed worker 持续推理或特定批确定性 `exit 133`（SIGTRAP），无 stderr。
- **诊断**：先怀疑 53KB 超大块（嵌入取块首 2000 字防护）；再发现是特定批确定性崩溃（重试同批反复死）；最终判定为 ONNX 会话级陷阱。
- **修复（崩溃自愈）**：跳过已入库块续传 + 每批落盘（跨重启可续）+ 批失败逐块二分定位 + 毒块跳过（词法通道仍覆盖）+ worker 崩溃自动重启重试。
- **结果**：663/663 全入库、0 跳过。`reindex` 同样加嵌入长度保护。

**困难小结**：Linux 路径 bug（`fetch-models.mjs` 的 `file:///` 拼绝对路径变四斜杠 + 找错 dist 目录）、ONNX 陷阱、超大块、worker IPC 用错 API（见 §5.1）。

## 4. 主线三：回答内容检索

### 4.1 双通道融合

- **词法通道**：BM25 + 别名 + 意图加权，零模型、毫秒级，擅长精确术语。
- **稠密通道**：BGE-M3 语义向量，擅长同义/跨域消歧。
- 两路 **RRF（倒数排名融合）** 合并，再按摘要配额裁剪。

### 4.2 跨域同形词撞车（本会话核心修复）

词法通道会把 `costmap` 的 map 撞 C++ `map`、"观察者模式"撞"工厂模式"——KB 明明有覆盖却检索错配。诊断确认是**匹配缺口而非覆盖缺口**后：

- 补消歧别名（观察者→observer/发布订阅/通知；costmap→代价地图/膨胀/Nav2；AMCL→粒子滤波/蒙特卡洛 等）。
- 启用稠密通道做语义消歧。
- **效果**：21 题黄金集词法 Hit@5 从 0.833 提到 **1.000**（MRR 0.909）；8 题实测命中正确率 **8/8**。

### 4.3 追问与投机检索

- **追问查询扩展**（本会话）：短追问/指代句（"那…呢？/它…"）检索易 miss，自动拼接上一问做检索扩展（仅检索用，提示词保留原问）。实测裸"那迭代器失效呢？"0 命中 → 扩展后 5 命中。
- **历史保真**（本会话）：历史按总预算（2400 字）从最新往回保留，保住最近完整轮，追问的上文不被裁掉。
- **投机检索**（历史 `58a3e5f`、`7988671`）：从实时 ASR partial 预取检索（精确文本缓存、按会话隔离），句子关闭时复用已飞行的检索结果。

### 4.4 评估

`tools/kb-eval.ts` 用黄金题集测 Hit@k/MRR/关键词覆盖，且**故意不喂答案键里的 job/intent**（生产环境靠猜，测量也猜），数字比基线低不是回归。检索改动一律先测再断言。

## 5. 主线四：回答内容准确度

### 5.1 先修一个让知识库彻底失效的根因

知识库一直"加载中"、检索不到任何内容——根因不是模型，而是 **embed worker 用错了 IPC API**：`embedWorker.ts` 用 `process.on('message')`/`process.postMessage()`（child_process.fork 的 API），但 Electron `utilityProcess` 子进程只认 `process.parentPort`，init 消息永远收不到，worker 空转。`embed-probe.cjs` 复现：修复前 120s 全静默，修复后 ready 208ms。按 ASR worker 已有的 parentPort 模式修复。

### 5.2 忠实度 / 真实性 / 口吻约束（本会话）

提示词层加共用硬约束（自由+面试模式）：

- **忠实度**：召回材料相关时，回答须覆盖其核心结论与关键术语，数字/口径/机制不得改写或省略。
- **真实性**：不得编造材料之外的公司/项目/数字/指标；通用知识须准确，无把握给稳妥说法而非臆测。
- **口吻**：以本人已掌握的知识直接作答；禁止"知识库/资料/检索/依据你项目资料"等来源性措辞；禁止请对方贴代码、承诺逐行核对、说"需要查代码"；不确定细节直接省略。

### 5.3 实测

8 题（含全部曾错配主题）：检索命中正确率 **8/8 = 100%**，回答核心关键词覆盖 **15/18 = 83%**（3 处为同义改写，语义已覆盖），禁语 **0/8**。

### 5.4 历史 accuracy 机制

- 准备答案直答：`问：…答：…` 自动识别成问答对，命中先原样显示再充实（离线、几十毫秒）。
- 口径冲突标记：材料带 ⚠/口径不一致/待核 时，提示词强制列出各口径及出处，不挑一个念、不折中编造。
- 摘要配额防挤占（`f14a56b`）：检索块被摘要配额裁剪后重新填满。

## 6. 主线五：回答延迟等待

### 6.1 先把应用成本剥离出来（历史 `525aa5a`）

用 mock-llm（延迟已知）打生产适配器，把"我们自己的开销"从"网络+服务商"里干净剥出：

| 场景 | TTFT |
|---|---|
| gate（376 字） | min 1 / p50 2 / p95 14ms（14 是首次预热） |
| answer-short / context | p50 1ms |
| 提示词组装（最坏 1.58 万字/16 条） | **0.032ms/次** |

**结论**：应用侧"拿到句子→开始收字"只花 1–4ms。余下延迟只有两个来源——服务商往返、我们自己设的定时器。这推翻了"缩短防抖省成本"的原方案：1100ms 防抖不是省成本，是纯等待。

### 6.2 投机作答（历史 L4，`f704ec5`/`a145738`）

句子一关闭就发请求、需要时 abort 撤销，而非猜更短等待。三个洞由"重读它承诺了什么"发现：VAD 没说怎么关闭的（flush 会发起无人读的回答）→ reason 贯穿链路；首 token 已渲染还撤销会清空用户在读的答案 → streamed 标志阻止合并；碎句无限撤销 → 上限 2 次。默认关闭（涉及重复计费，需产品决策）。

### 6.3 前缀缓存与流式（本会话核心修复）

- **流式绕路**：`answerWithVision=true` 时纯文本回答也走 `visionChat`（`stream:false` 整段等待），首 token 9.6–23.7s。改为只有含图片才走视觉通道，文本回答一律流式。
- **前缀缓存结构**：自由模式此前把逐题变化的 RAG 塞进 system，前缀每问都变、cache_hit 恒 0。重构为稳定 system 头（指令+简历/JD/笔记）+ 可变 user 内容。
- **prewarm 守卫**：面试模式稳定前缀的预热曾被 vision 开关误禁，修复后恢复。
- **历史裁剪**：总预算制降低 prefill（4388→~1500 token）。
- **空回答重试**：provider 偶发零内容完成，自动重试一次。
- **死路由超时**（历史 `9393c4e`）：不在死路由上无限等待。
- **先答后补**（历史 `1f11a4c`）：联网检索作为答后追加块，不阻塞首字。

### 6.4 实测与诚实边界

- 本会话修复后首 token **1.2–4.3s**（此前 9.6–23.7s）。
- **新题冷测**（8 道从未问过的题，排除缓存美化）：首题 2547ms、中位 2059ms、范围 628–4793ms——证明此前数字非缓存假象，provider prefill + 负载波动主导。
- **诚实边界**：DeepSeek 前缀缓存有 1024 token 门槛，无资料的自由提问头太小，命中间歇；真实 provider TTFT 需用户在自己 shell 给 key，标为未测。应用侧已做到位，再压只能换更快 provider 或精简 prompt。

## 7. 困难与经验教训（汇总）

1. **根因常在意外处**：知识库失效不是模型而是 IPC API 用错；回答慢不是检索而是非流式绕路；ASR 1.85s 不是时间戳偏置而是端点化粒度。先复现、定位到行，再改。
2. **测量诚实**：测量台会静默产假数据（端口占用、二进制日志、EPIPE、共享时钟）。反常数字先怀疑测量台。未测到的不假装测过。
3. **provider 约束要前置澄清**：DeepSeek 无 embeddings 接口、前缀缓存 1024 token 门槛、温度被某些模型钉死（Kimi，`d686623`）——这些决定方案可行性，先查清再设计。
4. **崩溃自愈优于硬失败**：ONNX 陷阱不可控，灌库做成续传+二分+跳过+重启，把不可控降级为可恢复。
5. **契约测试的 pin 要随有意变更更新**：稳定前缀字节、风格指令行有 pin 测试防意外漂移；有意改动时同步更新 pin，而非删测试。
6. **保留作者边界**：检索准确率的关键之一是不要滑窗重切问答表格/公式；预切分通道 Hit@5 显著高于滑窗。
7. **授权边界**：凭据不进命令、live 实例重启与提交先获授权、涉计费变更需产品决策。
